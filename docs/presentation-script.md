# 项目代码与网页讲解稿

> 用途：组内分享或中期答辩前的表达底稿。先按代码导读理解，再改成自己的话，不要机械照背。
> 全程统一口径：**当前完成的是可复现的算法仿真链路，不是真实水域实测，也尚未形成硬件控制闭环。**

## 一、5 分钟代码讲解

### 0:00—0:35｜先讲项目解决什么问题

我们项目叫“听水·知微”，目标是利用四个水听器组成的圆阵，对水下异常声音做检测、测向和分类。换成三个问题就是：什么时候有声音、声音从哪来、它更像哪类目标。

目前我们把这条软件链路用仿真数据跑通了，并且做了可视化工作台。今天我主要展示代码怎样串起来，以及哪些结果已经验证、哪些还没有验证。

### 0:35—1:20｜打开 `run_pipeline.py`，讲总入口

这是完整流水线入口。最上面的 `FS`、`R`、`C` 分别是采样率、圆阵半径和水中声速。`EVENTS` 定义了一个 8 秒仿真场景：1 到 3 秒是 60 度方向的船舶声，4 到 5 秒是 120 度方向的人员拍水，5.5 到 7 秒是 250 度方向的鱼类活动。

程序首先生成四通道背景噪声，再把三个事件按照指定时间、方向和信噪比加入。这里使用固定随机种子，所以演示结果可以复现，而不是每次随机挑一个好看的结果。

接下来主流程只有三步：CH1 做 CFAR 检测；每段告警截取一秒，用四通道做 CBF 测向；再用 CH1 的 log-Mel 特征做 MLP 分类，最后输出告警。

### 1:20—2:00｜打开 `sim/uca_sim.py`，讲为什么四个通道能测向

同一个声源到达四个水听器的时间有细微差别，这个差别和入射方向有关。代码先根据四个阵元的位置和声源方向计算相对时延，再在频域乘相位因子，把时延加到每个通道上。

所以四个通道不是简单复制，也不是四段无关声音。测向利用的正是通道之间的相位差。也正因为有相位差，检测和分类不能直接把四通道普通平均，否则高频部分可能相互抵消，所以这两步先取参考通道 CH1。

`sim/sources.py` 则定义了不同声音的仿真结构：船舶偏低频谐波，拍水是宽带脉冲，鱼类活动是高频短促咔哒。这里必须强调，它们是仿真规则，不是真实水声数据集。

### 2:00—2:50｜打开 `src/detect/cfar.py`，讲检测

检测部分不是设一个固定功率阈值，而是让门限跟随背景变化。它有两路：一路沿频率找突出的谱线，主要抓持续的船舶声；另一路沿时间看总能量抬升，主要抓拍水这类宽带瞬态。

两路任一命中后，还要满足最短连续帧数，并合并相隔很近的片段，才形成告警，避免一个孤立毛刺就直接报警。

页面上统一用 0 dB 做判决线，因为代码已经把检测量除以对应门限并转成对数。这里显示的检测统计量不是信噪比。

我们曾经发现 Hann 窗使相邻频点相关，导致白噪声下帧级虚警率高于预算，所以频谱检测改为矩形窗，并增加了回归测试。当前校准结论只适用于仿真白噪声，不能直接搬到真实水域。

### 2:50—3:35｜打开 `src/doa/cbf.py` 和 `music.py`，讲测向

CBF 的思路比较直观：程序扫描 0 到 360 度，假设声音来自某个方向，就按这个方向补偿四个通道的相位再叠加。补偿正确时叠加功率最大，所以方位谱峰值就是估计方向。

我们还实现了 MUSIC 对比。它把协方差矩阵分成信号子空间和噪声子空间，真实方向的导向矢量应接近与噪声子空间正交，所以谱峰更尖。

但谱峰更尖不等于已经证明真实精度更高。MUSIC 对信源数、多途和相干信号更敏感，所以当前主流水线仍用 CBF，MUSIC 作为独立对比结果。

### 3:35—4:20｜打开 `src/classify/`，讲分类

分类前先把一秒波形转换成 40 维 log-Mel 时频特征。可以把它理解成一张声音纹理图：低频线谱、宽带拍水和高频咔哒在图上的分布不同。

当前模型是一个含 128 单元隐藏层的轻量 MLP。训练数据由四类仿真生成器产生，默认每类 200 条，再按八二比例划分训练和测试。

这里要区分三个数字：某次输出的模型分数、测试集准确率、现实中的可信度。它们不是一回事。当前 96.2% 只对应这套仿真数据划分，而且 MLP 分数没有经过真实数据校准，所以页面上写的是“模型得分”，不写成现实置信度。

### 4:20—5:00｜打开 `src/viz/export_demo.py`，讲网页为什么可信

这个导出脚本复用前面的仿真、检测、测向和分类函数，把实际输出整理成 JSON，包括四通道波形包络、CFAR 序列、方位谱、log-Mel 和四类模型得分。

前端只负责展示和交互，不在页面里手填算法结果。JSON 中也写明了 `dataMode` 是 `simulation`，页面顶部和底部都持续标注仿真。

最后，我们用 8 项 Python 测试锁住事件写入、SNR、低频检测、虚警率、选频和定长输入等关键行为；前端还有桌面交互、移动端布局和数据失败重试测试。测试通过说明当前实现可复现、关键行为没有回归，但不等于完成真实水声性能验证。

## 三、老师追问时的简短回答

### 1. 你们现在真正完成了什么？

完成了可复现的四通道仿真、CFAR 检测、CBF 测向、MLP 分类和可视化联动，并保留自动化测试和运行记录。没有完成真实水域验证和硬件闭环。

### 2. 为什么用圆阵？

圆阵可以扫描 0 到 360 度，避免线阵左右舷镜像模糊，适合全向监测。当前四元小孔径方案仍需在低频、多目标和真实噪声下继续验证。

### 3. 为什么用 CFAR？

因为背景噪声会变化，固定阈值难以同时兼顾漏报和误报。CFAR 根据周围参考单元动态估计背景，当前还用谱线与能量两路覆盖不同目标形态。

### 4. MUSIC 为什么没进主流水线？

我们已经实现并做了对比，但它需要信源数等先验，对相干和多途更敏感。当前先用 CBF 保证主链路稳定，后续有足够实验条件再评估替换。

### 5. 96.2% 是真实准确率吗？

不是，只是当前仿真数据划分的测试结果。训练和测试共享仿真生成规则，所以需要公开数据、实测数据和更严格的独立划分来验证泛化。

### 6. 为什么页面显示模型得分而不是置信度？

因为 softmax 输出未经校准，单个样本的高分不等于现实中有相同概率正确，所以使用更准确的名称。

### 7. 网页结果是手工填的吗？

不是。`src/viz/export_demo.py` 复用算法代码生成 JSON，前端读取该文件；固定随机种子用于复现。页面中的场景真值只用于对照误差。

### 8. 下一阶段最重要的工作是什么？

先固定真实数据接口并接入公开或实测数据，重新做检测、测向和分类验证；同时把硬件 BOM 草稿推进到可采购、可装配、可水密验证的工程方案，而不是直接宣称已经能部署。
